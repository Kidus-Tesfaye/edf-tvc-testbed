*Date: 2026-09-17 · Audience assumed: student-conference reviewers · Reviewer: Claude (Opus 5, via Claude Code) ·
Search bound: delta audit on top of the solid-motor review of the same date — surveys, system papers, recent preprints and same-tier builds for electric-ducted-fan vehicles, one citation hop; "recent" cut-off 2025-03. Source keys S1–S35 refer to the earlier report's table and are repeated below only where cited; new sources start at S36.*

**Statement under review (verbatim, now applied to an electric-ducted-fan vehicle; starting point: the BB Projects "SpaceX-inspired EDF rocket" <a href="#s36" title="S36: B. Brocken, 2021-02-27, &quot;SpaceX inspired EDF rocket&quot;, BB Projects (bbprojects.technology) project page — starting point supplied by the user; counter-example SC1 and SC2 (flown, stock ArduPilot SingleCopter); read: full text; verified: yes — page (70 mm 6S EDF, about 2.5 kg thrust, Pixhawk/ArduPilot 4.0.4 SingleC…">[S36]</a>):**

> Active stabilisation of vertical thrust is a stretch problem for student teams; commercial model rockets use passive fins and aren't designed for control experimentation.

## Verdict

**Not defensible** — confidence high for the statement as written under electric propulsion; a narrower, EDF-specific statement (below) is defensible after narrowing, confidence medium.

Switching to an electric ducted fan (EDF) does not narrow the original gap — it removes it. Every clause now points at something that demonstrably exists. Attitude stabilisation of an EDF "rocket" was flown by the starting-point project itself in 2021 on a stock open-source autopilot configuration (ArduPilot SingleCopter: one fan, four vanes) <a href="#s36" title="S36: B. What survives is one specific, documented hole at the student tier — closed-loop *horizontal* position control with low-cost onboard sensing, which the one published thesis reports it could not achieve — and one not-found-by-search absence: an open EDF testbed publishing a validated plant model with a like-for-like comparison of controllers on the same airframe.

### SC3 — a platform for control experimentation

ArduPilot's developer documentation describes a custom-controller library that "allows you to implement and easily run your controller inside ArduPilot in a systematic way": the user's controller receives the attitude targets, outputs roll/pitch/yaw commands, runs "after the main rate controller ... and before the motor output library", is enabled per axis via `CC_AXIS_MASK`, can be switched in and out in flight via RC option 109, and returns to the stock controller with "bumpless transfer" <a href="#s41" title="S41: ArduPilot Dev Team, n.d. ## Reconciliation

- **Solid-motor review said "university teams stall at static fire"; the electric tier says a single student hovered and landed.** Both are right, and the difference is the propulsion: an EDF gives minutes of throttleable, restartable thrust and can be tested tethered and indoors, so the iteration loop that took Barnard "four years" and ten failed launches on solid motors <a href="#s12" title="S12: J. Barnard, K. Hammond, 2019, &quot;Build Your Own Thrust Vectored Rockets for Vertical Landings Like SpaceX&quot;, Make: — carried over; the solid-motor iteration cost being contrasted; read: full text; verified: yes — article (earlier report)">[S12]</a> collapses to bench and tether sessions. The "stretch" premise was a solid-motor premise. Resolution: drop it.
- **The statement's "commercial platforms" clause and the off-the-shelf reality point in opposite directions.** Under EDF the COTS baseline *is* the actively stabilised vehicle <a href="#s40" title="S40: ArduPilot Dev Team, n.d. (page current 2026-09-17), &quot;SingleCopter and CoaxCopter&quot;, ArduPilot Copter documentation — counter-example SC2 (stock support for a one-fan, four-vane vehicle); read: full text; verified: yes — page (`FRAME_CLASS` 8/9, vane servo mapping and parameters)">[S40]</a>, and the COTS autopilot *is* the experimentation hook <a href="#s41" title="S41: ArduPilot Dev Team, n.d. (page current 2026-09-17), &quot;Adding a Custom Controller&quot;, ArduPilot developer documentation — counter-example SC3 (experimentation hook in the COTS autopilot); read: full text; verified: yes — page (`CC_TYPE`, `CC_AXIS_MASK`, RC option 109, bumpless transfer, &quot;tested only lightly&quot;)">[S41]</a>. Resolution: the project cannot claim to supply a platform the market lacks; it can claim to *use* that hook to run experiments nobody has published for this vehicle class.

## Rewritten statement

> Electric-ducted-fan "rockets" steered by exhaust vanes or a gimballed fan have been hovered and landed by hobbyists on a stock ArduPilot SingleCopter configuration and by a Master's student with custom 100 Hz avionics, and research groups now use electric thrust-vectored vehicles as their standard low-risk testbeds; attitude stabilisation of such a vehicle is a configuration task, not a research gap. What has not been shown at the student tier is closed-loop horizontal position control of an EDF vehicle with low-cost onboard sensing — the one published thesis reports it failed on vibration-corrupted optical flow — and no open EDF testbed publishes a validated plant model together with a like-for-like comparison of controllers flown on the same airframe. This project builds an open EDF thrust-vectoring testbed from the BB Projects design, identifies its plant model from flight data, and uses ArduPilot's custom-controller hook to compare [two or three named controllers] on identical hardware.

## Implications for the project

Not part of the audit, but the evidence changes the three-month plan more than it changes the statement:

- **EDF fits the timeline; solid motors did not.** Start from <a href="#s36" title="S36: B.
